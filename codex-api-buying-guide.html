CODEX API BUYING GUIDE

低价线路为什么
可能反而更贵？

Codex 不是一次问答。读仓库、改文件、调用工具、跑测试，任何一次断流或重试都可能重复计费。购买前真正该比较的是：完成一次真实任务，到底花了多少钱。

先给结论：不要把“每百万 Token 单价”当成购买理由。固定一个真实仓库任务，连续跑 3 次；完成修改且测试通过，才算成功。

一、最容易被忽略的三笔成本

失败重试请求失败不代表没有产生 Token 或网关成本；重跑会再次消耗上下文。
SSE 断流短问答正常，不代表长任务能持续返回事件并完成工具闭环。
无效成功能回复“你好”不算成功；代码改对、测试跑通才是开发任务完成。

二、用这个公式比较，而不是凭感觉

每次成功任务成本 = 总计费成本 ÷ 成功任务数 总计费成本 = 每次尝试成本 × 平均计费尝试次数 × 任务数 成功任务数 = 任务数 × 真实任务成功率

例子：A 线路每次尝试 ¥0.60，平均要尝试 1.6 次，成功率 70%；它每次成功任务约为 ¥1.37。B 线路每次尝试 ¥0.80，平均 1.05 次，成功率 95%；每次成功任务约为 ¥0.88。B 的标价更高，但真实任务反而便宜约 36%。这只是演示，必须用自己的账单和任务数据替换。

三、购买前只做 5 项验收

  1. 认证：API Key 能否正常鉴权，错误时是否明确返回 401。
  2. 协议：是否支持 Codex 使用的 Responses 接口，而不只是普通 Chat Completions。
  3. 长连接：长任务的 SSE 是否持续，出现 429、502 后能否合理恢复。
  4. 工具调用：读文件、写文件、执行测试能否形成完整闭环。
  5. 账单：控制台 Token、重试次数和最终扣费能否相互对上。

OpenAI 官方 Codex 高级配置文档说明，自定义 Provider 可以配置 base URL、认证方式和 wire API；Provider 相关配置应放在用户级 ~/.codex/config.toml，项目级配置会忽略 model_provider 和 model_providers 等凭据重定向设置。官方文档也列出了 API 请求、SSE 事件、工具结果和 Token 用量等可观测事件，可用于自己的验收记录。

四、怎样把试错风险压到最低

  1. 不要先买大套餐；只投入你能接受全部损失的小额预算。
  2. 固定仓库、模型、任务和验收标准，不要边测边换题。
  3. 至少连续测试 3 次，分别记录耗时、重试、Token、扣费和最终结果。
  4. 任何一家 Provider 都用同一套表格对比，不给品牌加主观分。
  5. 只有连续任务表现符合预期，才扩大充值。
