Codex 配了第三方 API，
为什么仍走默认线路？

先别急着更换 API。很多“线路不生效”其实是配置层级放错了：项目级配置会主动忽略 Provider 和认证相关键。

更新：2026-10-12 · 依据 OpenAI 官方 Codex Advanced Configuration

最常见原因：你把 model_provider、model_providers 或 openai_base_url 写进了仓库的 .codex/config.toml。这些键会被忽略并触发启动警告。

正确位置：用户级配置

自定义 Provider 应放在 ~/.codex/config.toml。如果改过 CODEX_HOME，实际位置是 $CODEX_HOME/config.toml。

model = "从控制台复制的当前可用模型名"
model_provider = "your_gateway"

[model_providers.your_gateway]
name = "Your Gateway"
base_url = "https://你的网关地址/v1"
env_key = "OPENAI_API_KEY"
wire_api = "responses"

env_key 填环境变量名称，不是真实 API Key。密钥不要放进网页、截图、公开仓库、Issue 或群聊。

5 分钟排错顺序

  1. 确认文件是 ~/.codex/config.toml 或 $CODEX_HOME/config.toml。
  2. 从项目 `.codex/config.toml` 移除 Provider 与认证键。
  3. 检查顶层 model_provider 与 Provider 表 ID 是否完全一致。
  4. 使用控制台当前模型名，修改后重新启动 Codex。
  5. 先做小任务，再用同一真实仓库任务连续跑 3 次。

用一次性覆盖快速分层

Codex 支持使用专用参数或 --config 覆盖单次运行。先临时指定模型：

codex --model "当前可用模型名"

如果单次覆盖生效，常规启动却仍走旧设置，优先检查配置文件位置、层级与拼写。如果二者都失败，再检查模型名、鉴权、Responses API 和网关兼容性。

什么时候才应怀疑 API 线路？

  • Responses API 无法建立或事件结构不完整；
  • SSE 长任务频繁无错误断流；
  • 工具结果返回后无法继续；
  • 失败重试造成重复扣费或用量无法核对；
  • 同一个小任务连续 3 次无法稳定完成。
